Use the app at `/Users/justinyek/Code/dreamforge-source` and its maintained instructions in `docs/e2e/prompting.md`.

Run `npm run test:prompting` for deterministic harness regression checks, then `npm run test:e2e:prompting` for live API integration. The live suite uses `.env.e2e.local`, records `.e2e-results/latest.json`, and only modifies a fresh dedicated E2E Prompting Playground project. The runner always deletes that project, its Runtime snapshots and its Supabase records in `finally`, on success or failure. For manual test projects include a fresh UUID `e2eRunId` in the creation payload so cleanup can identify the explicit disposable-test opt-in. Never disable this cleanup or leave manual E2E projects behind; verify removal and preserve only reports/screenshots. Keep credentials private; do not copy them into messages, reports or source control. Provision a dedicated student via `npm run test:e2e:setup` only if setup is needed and the requested environment is configured. Stop after the first live failure and inspect the report; do not hide failures with repeated model retries.

The command tests the real backend/model/runtime/database path, not browser interactions. For a full UI smoke test, set `E2E_BROWSER_EXECUTABLE` to the local Chrome executable so the runner tests browser interactions before automatic cleanup. If doing a manual browser investigation, create a disposable E2E project and delete it and its snapshots/Supabase data in a finally block afterward. Use available browser-control tools to sign in with the dedicated test account, open the report's test project, submit a short edit, verify progress and final written reply, interact with the generated counter (Add one and Reset), reload and verify history. Follow the browser tool's supported APIs; do not extract cookies or browser internals. Save a screenshot as evidence. Avoid using a real student's project, changing their wallet or publishing the test app.

Report checks that passed and failed, first feedback/text and total duration from the JSON report, and whether browser interaction was actually tested. A visible progress heartbeat is not model text. HTTP 200 alone does not prove a playable app; tool output alone does not prove a completed reply. Live tests consume the configured model/runtime allowance. If credentials or capacity are unavailable, state the blocker instead of reporting the live test as passed.
