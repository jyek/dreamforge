# Child policy and reliable execution (Phases 1 and 2)

Implemented on 17 October 2026. The production migration and protected runtime initialization are applied; rollout validation is recorded below. This change does not migrate to Pi or add the learning controller.

## Server-owned child policy

`lib/child-policy.ts` resolves authentication, provider approval, moderation, spending and sharing policy from server settings. Coding capabilities are now enabled for child and teacher accounts: terminal access, package installation, public GitHub repository imports and general source tools. Anonymous protected demo generation still requires an authenticated, funded account.


All protected generation requires `STUDENT_AI_PROVIDER_APPROVED=true` and semantic moderation. Configure either `STUDENT_MODERATION_URL` plus `STUDENT_MODERATION_KEY`, or `STUDENT_MODERATION_PROVIDER=openrouter` plus a server-only `OPENROUTER_API_KEY`. The built-in route uses GPT OSS Safeguard, bounds requests, charges moderation to the same atomic account budget, and fails closed. Both moderation and coding requests enforce OpenRouter zero-data-retention routing and deny data collection at the final HTTP request, including retries and fallbacks. The strict moderation contract applies to input, tool content, and output in both login systems. The local rules are an additional check, not a replacement for configured moderation. Set provider approval only after approving model/provider routing, retention and student-data terms, including fallbacks. Platform wallets and legacy classroom daily reservations remain atomic; unknown usage remains reserved for review.

Image attachments are enabled for authenticated learners using GLM or DeepSeek, with a maximum of three inline PNG/JPEG/WebP/GIF images and 2 MB total per message. The composer shows the attachment button. Repository imports and terminals are enabled; student publishing still requires teacher approval. Historical image parts are replaced with text placeholders before protected history is sent to a model. Text moderation and identity redaction exclude encoded image data; there is no dedicated image moderation pass.

## Runtime boundary and private previews

Project VMs use Runtime's normal public-web networking policy. `lib/prepare-project-runtime.ts` replaces the previous child-runtime initializer. Existing restricted workspaces are migrated once: source ownership returns to the normal VM user, old app-user processes are stopped, the restrictive Next config is backed up and replaced, and the dev server restarts normally. New projects and recovered snapshots receive the same preparation. The server does not copy its account credentials into projects.

Previews remain authenticated and use a separate opaque origin so generated code cannot read DreamForge account cookies. Their content policy now permits external scripts, assets, forms and API connections. Asset capabilities remain project-scoped and short-lived. These access controls protect project/account ownership; they no longer impose child-specific coding or outbound-web restrictions.

Run `npm run runtime:prepare -- --apply` to migrate stored runtime bindings, or let a project prepare on its next access. The retired `runtime:secure-child` command and child-runtime initializer have been removed.

## Durable runs, revisions and recovery

Apply `supabase/migrations/202610170001_execution.sql`. Its service-only tables hold project revisions, one active run per project, snapshots, durable lifecycle/tool/verification events, cancellation requests, and approved shares. Browser database roles have no access to these tables.

Chat requests must include the displayed project revision. The server ignores browser-supplied assistant/tool history. Starting a run atomically claims the project lock and saves a pre-run Runtime snapshot. During capture, automatic wake is disabled and preview/source/runtime entry points decline wake-producing work. The idle sweeper excludes active runs. This prevents preview traffic from waking the machine mid-capture. Automatic wake is restored afterward; a new run owner can repair a flag left behind by a terminated worker. The response includes `x-dreamforge-run-id`. All tool calls are serialized, checked against the active run, and logged without source or prompt contents. Writes advance the revision and invalidate all verification before touching source. Adult demo mutating tools are tracked too; compilation/rendering evidence uses the same verifier.

Stop persists a cancellation request, aborts model generation, closes browser verification, and prevents further tool work. The lock is retained until in-flight tool work settles. Disconnecting the chat also aborts the run. A terminated worker's durable lock is retained rather than silently allowing another writer. An unconfirmed guest process also keeps its lock and is recorded as interrupted. After its five-minute deadline, snapshot recovery can mark it interrupted and replace its runtime. Recovery stops the former sandbox, changes the binding, increments the revision, invalidates verification, and refreshes the preview. Recovery uses disk snapshots and a fresh server process. Snapshots use Runtime's seven-day retention; recovery can fail after expiry or provider deletion. The former stopped sandbox is retained as a recovery safeguard and should be included in administrator retention/cost cleanup.

Project revisions synchronize silently after reload and during work so edit requests remain revision-bound. Internal revision, event and verification metadata is no longer displayed above the chat. The composer retains its Stop action; verification evidence and snapshot recovery remain available through the execution API. A conversation change alone does not roll back files.

## Evidence, not model wording

`checkAppTool` runs a bounded TypeScript compilation of project source against the trusted compiler options, excluding generated build-cache validators. It then uses a fresh browser context through `VERIFICATION_BROWSER_WS` (CDP), or bundled server-side Chromium when `VERIFICATION_BROWSER_BUILTIN=true`. A remote browser service must have approved data handling. Safe compiler file/line/error codes are returned without source snippets. Browser checks permit the external requests used by the project. Checks include HTTP availability, nonempty rendered content, uncaught/console errors, a screenshot hash, and up to eight named-button/expected-visible-text assertions. All results carry the checked revision. Unavailable browser capacity and incomplete or failed checks cannot produce `ok=true`.

Stored evidence distinguishes page loaded, number of buttons tested, and the learner's own acknowledgement; internal status metadata is not displayed above chat. A model cannot set the acknowledgement through a tool. Every edit clears it along with machine evidence. A passing generic render does not establish unspecified gameplay; add explicit interaction expectations and ask the learner to try the app.

## Truncated tool recovery and truthful completion (25 October 2026)

A production game request exhausted its 8,192-token model response limit while streaming file-write arguments. No write executed, but the UI displayed a generic missing-summary fallback and the run was recorded as completed. A later retry built the game, demonstrating that the initial failure was an incomplete tool request rather than the learner's wallet balance.

The model adapter now buffers tool argument fragments until a complete call exists. It can discard unexecuted truncated arguments and recover once across the run, asking for a small scaffold and focused follow-up patches. A step that emitted any complete tool call is never replayed. Each recovery settles the first provider call, reserves the next separately and checks cancellation; token limits and request timeouts still apply. Text continues streaming. The normal system instructions also favour small code writes rather than a whole game in one call.

Finish reasons reach the persisted fallback. A truncated response or unfinished tool receives a specific incomplete status, not a claim of success. A server-generated stream outcome and the provider finish reason determine the run state; length-limited, incomplete and prematurely ended streams are marked failed. A `generation.finished` event records finish reason and stream outcome. This distinguishes the agent ending normally from independent verification that the requested app works.

Browser navigation waits for DOM readiness instead of network idleness. Optional screenshot failure has its own evidence fields and cannot overwrite successful rendering or button checks. Missing browser checks, actual rendering failures, runtime errors and failed interactions remain unsuccessful.

Validation: 38 prompting unit tests, seven local provider/SDK simulations, four runner fixtures, 31 policy tests, 27 database/execution tests and the production build passed. Coverage includes actual SDK processing of truncated JSON, bounded recovery, no tool replay, per-call accounting, Stop and quota refusal, failed completion state, and screenshot failure preserving observed evidence. Live rollout validation is recorded separately after deployment.
